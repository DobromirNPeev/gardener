# Option 1 — Live KinD + Gardener e2e scenario (manual, operator runs it)

This proves end-to-end that, after Option 1, triggering a CA rotation on a shoot that has a
**blocking admission webhook on `configmaps`** no longer hangs, because gardenlet now only waits on
`kube-system/kube-root-ca.crt`. It also demonstrates the accepted tradeoff: `kube-root-ca.crt`
ConfigMaps in customer namespaces may stay stale.

You must run this yourself — it needs a local KinD cluster; the tester cannot run it here. Run
everything **from the Option 1 worktree**:

```

```

## 0. Two kubeconfigs

Local Gardener uses two clusters, each with its own kubeconfig generated by the dev setup:

- **Runtime / seed cluster** (where KinD, gardenlet, control planes run):
  `example/gardener-local/kind/local/kubeconfig`
  (same as `$(make)`'s `KUBECONFIG_RUNTIME_CLUSTER` = `dev-setup/kubeconfigs/runtime/kubeconfig`).
- **Virtual garden cluster** (where you create `Shoot`/`Project` objects):
  `KUBECONFIG_VIRTUAL_GARDEN_CLUSTER` = `dev-setup/kubeconfigs/virtual-garden/kubeconfig`.

Export convenience vars (adjust paths to the actual files printed by the bring-up):

```bash
export KUBECONFIG_RUNTIME=$PWD/dev-setup/kubeconfigs/runtime/kubeconfig
export KUBECONFIG_VIRTUAL=$PWD/dev-setup/kubeconfigs/virtual-garden/kubeconfig
```

IMPORTANT: `make` sets `KUBECONFIG` internally per target, so do **not** rely on a globally exported
`KUBECONFIG` for the `make` steps. For raw `kubectl` you pass `--kubeconfig` explicitly (below).

## 2. Create a normal shoot

Use the sample local shoot:

```bash
kubectl --kubeconfig "$KUBECONFIG_VIRTUAL" apply -f example/provider-local/shoot.yaml
```

Wait for it to reconcile to `Healthy`/`Succeeded`:

```bash
kubectl --kubeconfig "$KUBECONFIG_VIRTUAL" -n garden-local get shoot local -w
# wait for .status.lastOperation.state == Succeeded, type == Reconcile
```

Fetch the **shoot** admin kubeconfig (short-lived) so you can work inside the shoot cluster:

```bash
kubectl --kubeconfig "$KUBECONFIG_VIRTUAL" -n garden-local create \
  -f <(cat <<'EOF'
apiVersion: authentication.gardener.cloud/v1alpha1
kind: AdminKubeconfigRequest
spec:
  expirationSeconds: 7200
EOF
) --raw "/apis/core.gardener.cloud/v1beta1/namespaces/garden-local/shoots/local/adminkubeconfig" \
  | jq -r '.status.kubeconfig' | base64 -d > /tmp/shoot-admin.kubeconfig
export KUBECONFIG_SHOOT=/tmp/shoot-admin.kubeconfig
```

(If your version uses `gardenctl` or the `kubectl gardenlogin` flow, use whatever you normally use to
get the shoot kubeconfig; the only requirement is cluster-admin access inside the shoot.)

Confirm the shoot already has `kube-root-ca.crt` ConfigMaps in multiple namespaces:

```bash
kubectl --kubeconfig "$KUBECONFIG_SHOOT" get cm kube-root-ca.crt -A
# expect at least kube-system/kube-root-ca.crt and default/kube-root-ca.crt
```

## 3. Plant a blocking `configmaps` webhook in the shoot (with no backing pods)

This is the webhook that would, before Option 1, hang CA rotation when gardenlet tried to touch
`kube-root-ca.crt` ConfigMaps in customer namespaces. `failurePolicy: Fail` + a service with no
endpoints means every intercepted write is rejected.

Deploy it scoped to the `default` namespace (a customer namespace) so it does NOT interfere with
`kube-system`:

```bash
cat <<'EOF' | kubectl --kubeconfig "$KUBECONFIG_SHOOT" apply -f -
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: block-configmaps-in-default
webhooks:
- name: block-configmaps.example.com
  admissionReviewVersions: ["v1"]
  sideEffects: None
  failurePolicy: Fail           # <-- any failure to reach the webhook blocks the write
  timeoutSeconds: 10
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: default   # only customer namespace 'default'
  rules:
  - apiGroups: [""]
    apiVersions: ["v1"]
    operations: ["UPDATE","CREATE"]
    resources: ["configmaps"]
    scope: Namespaced
  clientConfig:
    # Points at a Service with no backing pods -> connection fails -> Fail policy rejects write.
    service:
      namespace: default
      name: nonexistent-webhook
      path: /validate
      port: 443
EOF
```

Sanity check that the webhook actually blocks ConfigMap writes in `default`:

```bash
kubectl --kubeconfig "$KUBECONFIG_SHOOT" -n default create configmap probe --from-literal=a=b
# EXPECT: Error ... failed calling webhook "block-configmaps.example.com": ... connection refused / no endpoints
```

And that `kube-system` is unaffected:

```bash
kubectl --kubeconfig "$KUBECONFIG_SHOOT" -n kube-system create configmap probe --from-literal=a=b && \
kubectl --kubeconfig "$KUBECONFIG_SHOOT" -n kube-system delete configmap probe
# EXPECT: both succeed
```

## 4. Trigger CA rotation start

On the **virtual garden** cluster, annotate the shoot:

```bash
kubectl --kubeconfig "$KUBECONFIG_VIRTUAL" -n garden-local annotate shoot local \
  gardener.cloud/operation=rotate-ca-start --overwrite
```

Watch the rotation phase and the shoot reconcile:

```bash
kubectl --kubeconfig "$KUBECONFIG_VIRTUAL" -n garden-local get shoot local \
  -o jsonpath='{.status.credentials.rotation.certificateAuthorities.phase}{"\n"}' -w
# expect: Preparing -> Prepared
```

## 5. Expected observations (the point of the test)

**With Option 1 (this worktree):** rotation does NOT hang.

- The CA rotation advances to `phase: Prepared`; the shoot's `lastOperation` reaches
  `state: Succeeded` within the normal reconcile time. gardenlet's
  `WaitUntilKubeRootCAConfigMapsUpdated` only lists/labels `kube-system/kube-root-ca.crt`, so the
  blocking webhook in `default` is never on its path.
- Verify gardenlet logs do NOT loop on the customer ConfigMap:
  ```bash
  kubectl --kubeconfig "$KUBECONFIG_RUNTIME" -n garden logs deploy/gardenlet \
    | grep -i "kube-root-ca.crt ConfigMap" | tail
  # expect: no repeated "do not yet contain the expected CA bundle" errors referencing default/customer ns
  ```
- `kube-system/kube-root-ca.crt` is labeled and holds the new bundle:
  ```bash
  kubectl --kubeconfig "$KUBECONFIG_SHOOT" -n kube-system get cm kube-root-ca.crt \
    -o jsonpath='{.metadata.labels.credentials\.gardener\.cloud/ca-bundle-name}{"\n"}'
  # expect: a non-empty ca-bundle secret name
  ```

**Tradeoff to record:** the `default/kube-root-ca.crt` (and any other customer-namespace
`kube-root-ca.crt`) may remain **stale** — it is neither labeled nor updated by gardenlet, and the
webhook keeps blocking writes to it. That is the deliberate cost of Option 1: rotation completes
instead of hanging, but customer-namespace trust bundles can lag until the webhook is fixed /
kubelet refreshes them.

```bash
kubectl --kubeconfig "$KUBECONFIG_SHOOT" -n default get cm kube-root-ca.crt \
  -o jsonpath='{.metadata.labels}{"\n"}'
# expect: NO credentials.gardener.cloud/ca-bundle-name label (left untouched)
```

**Contrast (optional, for the report):** on `master` (pre-Option 1) the same steps make the shoot
reconcile hang in `Preparing`, because gardenlet keeps failing to patch `default/kube-root-ca.crt`
through the blocking webhook. You do not need to reproduce this to validate Option 1, but it is the
baseline the fix addresses.
